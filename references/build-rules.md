## A. 体量档位（唯一口径）

| 档位 | 方块数 |
|---|---|
| 小建筑 | < 10,000 |
| **中型建筑** | 10,000 ~ 80,000 |
| 大型建筑 | ≥ 100,000 |
| 过渡带 | 80,000 ~ 100,000（口径未定义，必须明确归到中型或大型） |

**默认生成 = 中型，20,000 ~ 50,000 方块。** 要"更大"就明确升到大型（≥100k）并写进设计书。

可执行：`scripts/scale.cjs`；构建时 CLI 打印
`SCALE 中型建筑 30,648 方块（目标区间 20k~50k ✓）`，中型超区间会额外警告。

## B. 13 条风格无关原则

风格决定"长什么样"，这些决定"能不能立住"。换任何风格都不换。

| # | 原则 | 一句话做法 |
|---|---|---|
| P1 | 体量先行 | 先按 A 节定档位与方块数，再定细节 |
| P2 | 竖向要有锚 | ≥3 段高差、竖锚 ≥2 根；不要只放一根地标 |
| P3 | 形体参数生成 | 旋转体写剖面表 `[[层, 半径, 材质]]`；壳厚 ≥ 相邻层半径差 |
| P4 | 颜色按角色分档 | 每个色系 5 档 `wall / deep / roof / glass / tone`，禁止单色平铺 |
| P5 | 接缝靠画序 | 后画覆盖先画；被覆盖件要算"画到哪为止" |
| P6 | 入口是空间 | 见 D 节，判据是人能不能走过去 |
| P7 | 装饰要有承托 | 每件说得出靠下/上/侧面支撑，否则游戏里会掉 |
| P8 | 配色有上限 | 主体分组 ≤4；多色标识用 wool / 染色玻璃 / 未分组混凝土 |
| P9 | 先算后写 | 半径越界 / 层重叠 / 净空 / 门槛高差 / 宽高比，全部写进设计书 |
| P10 | 会砍 | 元素先估连通/支撑/验证成本，收益低就换简化版 |
| P11 | 分段输出 | 程序分段写，每段 `node --check` + `checkComplete` |
| P12 | 机器分≠好看 | 必须有能看清门窗檐口的观察手段才能交付 |
| P13 | 版本化 | 改动存新版，不覆盖 |
| P14 | **不复用历史参数** | 旧 builder / 旧作品只读"经验"，禁止复制尺寸、配色值、坐标与布局常数；新件必须写「与其他作品的差异」 |

### P14 怎么落地（分两种模式，别搞混）

**模式 A · 新建建筑**：禁止复用历史参数。

**禁止复用**（一律不许从旧文件里抄）：
- `size:[sx,sy,sz]`、画布尺寸、塔心距、半径、层高、方块目标数
- 色值（`#xxxxxx`）、材质词组合、`teamPalette` 的定档方式
- 坐标表、扇区角度、布局常数、绘制顺序里的具体数字

**允许复用**（这是"经验"）：
- 方法与结构：剖面表旋转、局部坐标系、5 档色阶、画序纪律、闸门用法
- 判据与陷阱：入口净空、门槛高差、壳厚 ≥ 收差、虚空间判定
- 失败模式与修复手法

**模式 B · 修改已有建筑**：**必须**沿用原建筑参数。

- 以原 builder 为基准：尺寸、坐标系原点、塔心距、色值、色阶档位、布局常数**全部保持不变**
- 只改被要求改的部分；不改无关参数，避免"顺手重做"导致与原作品不一致
- 提交时声明 `--base <原builder>`，检查器会把它当作预期基准而不是抄袭
- 设计书里写清：基准是谁、**保留了什么**、**改了什么**

**怎么证明**：设计书必须有「与基准建筑的关系」一节（新建写差异，修改写基准与改动范围）。
`require_design.cjs` 把这一节列为必需项。`check_reuse.cjs --base <原builder>` 会比对：
- 新建模式：与既有 builder 尺寸+常数重合过高 → `REUSE SUSPECT` 报警
- 修改模式：与 `--base` 的重合是**预期**，只报"相对基准改动了哪些维度"

## C. 设计书（写代码前必做，硬闸门）

写到 `output/design/<builder名>.md`；模板 `references/design-doc-template.md`。

**八节缺一不可**：判据 / 体量（含档位声明）/ 布局（标清半径原点）/ 预检算式（≥8 行带数字）/
画序（含停止边界）/ 风险 / 砍掉项 / 验收。

`require_design.cjs` 会校验：缺文件、缺节、缺档位声明、带数字行 <8 → **`design=BLOCK`，不生成**。
`--skip-design` 只用于调试，交付禁用。

**为什么强制**：边写边想的代价是 6~8 轮返工；结构级错误（桥接不上塔）事后只报"12,214 悬空"，
看不出根因。纸面上算错的方案，在代码里只会更贵。

## D. 入口与可通行（1×2 碰撞箱）

- 门/门洞净空 **≥2 格**（实际常用 4~6 格）
- 门槛相对室外地面高差 **≤1 格**，超了必须补台阶
- 门内侧不得被地板/家具堵住；入口前后贯通
- **不必装门板**：棚屋/谷仓/废墟/工地用 2 格高开放门洞更合理
- builder 必须导出 `entries: [{x,y,z,facing}]`（y = 玩家脚下那格）

校验：`checks.walkableReport`（阻断）+ `verify_reachable.cjs` 洪泛（最终证明）。

## E. 四道硬闸门 + 三项自检

| 闸门 | 判什么 | 不过 |
|---|---|---|
| `design` | 设计书与算式 | `design=BLOCK`，不生成 |
| `aesthetic` | 配色分组 / 悬空 / 比例（按最大连通体）/ 剪影 / 细节密度 | `aesthetic=BLOCK` |
| `walkable` | 门洞净空 / 门内侧 / 门槛高差 / 入口接近 | `walkable=BLOCK` |
| 一致性 | `SCAN_DISCONTINUITY` / `SCAN_DISSONANCE` 必须为空 | 返工 |

自检（报告，不阻断）：

| 自检 | 用途 |
|---|---|
| `checks.supportReport` | 灯笼/旗/藤/链/栏杆的承托，报数量与坐标 |
| `checks.headroomReport` | 室内净空分布（≤2 / 3~5 / 6+ 格） |
| `scripts/verify_reachable.cjs` | 从门外洪泛，证明真的走得到室内 |
| `checks.stairFacingReport` | 楼梯 `facing` 是否等于上升方向（启发式 warning，见 H 节 / E-005） |

## F. 施工顺序（通用）

```
地面/地形 → 广场/走道 → 桥/连接件 → 主体 → 塔/楼 → 装饰 → 补景 → 输出
```

后画覆盖先画。每个被覆盖件在绘制顺序表里写停止边界。

---

## G. 交付定义

四闸门全过 + 洪泛目标点全 `REACHABLE` + `supportReport=0` + 报出 `SCALE` 档位 = 才算完成。
未通过一律内部返工，不输出给用户。

## H. 方块状态约定（楼梯 / 门 / 半砖）

**楼梯 `facing` = 抬高半块所在方位 = 上升方向**（不是"模型朝向"，也不是下降方向）。

- 语义**取真值**，不要凭记忆推：解客户端 jar 的 `assets/minecraft/models/block/stairs.json`
  （抬高半块在 `[8,8,0]→[16,16,16]`，即 +x/东侧）配 `blockstates/*_stairs.json` 的 facing→旋转映射
  （east=0°，south=90°，north=270°，west=180°）。合起来即 facing 指向抬高半块。
- 想让玩家**沿 +z 往上走**写 `facing=south`；沿 −z 往上走写 `north`；沿 ±x 同理。
- 檐口 / 翘角 / 桥头这类"外端低、内端高"的装饰楼梯，`facing` 指向**朝内**（上升方向）；
  想让"坡度朝外泻"，是让朝外那侧自然成为低端，而不是把 facing 写成朝外。

**跑段与叠块（比 facing 更容易错，且闸门不看）**：

- **低端朝向入口/动线来向**：梯段从靠近门的一侧起坡、向远端升。把最高一级怼在门口，
  玩家一进门先撞梯体断面，观感就是"楼梯倒着"——此时 facing 写对了也没用。
- **每级只放 1 块楼梯**，梯体下方用**整块实心**填充；不要用同高楼梯去填，否则出现同柱
  双块、双层错台与悬挑半砖。
- **楼板洞口**必须覆盖"梯面 +2 会撞顶"的上部几级，否则梯段中段顶头。

**机器自检（都是启发式 warning，不阻断，也不等于全对）**：

- `checks.stairFacingReport(a)`：反侧斜上有体量、facing 侧没有 → 疑似反向。
- `checks.stairRunReport(a,{entries})`：同柱重复；高端比低端更靠近声明入口。
- 构建 CLI 自动打印 `STAIR …`；`--no-stair` 可关。
- 渲染器把楼梯画成整格，**看图看不出踏步走向**——最终仍要实机上下走一遍或看正交剖面。
