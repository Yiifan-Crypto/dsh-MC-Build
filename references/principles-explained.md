# 风格无关的建造原则（Universal Build Principles）

> 来源：mcarch.cn 的作品库（12 件，跨越东方仙宫 / 西式学院 / 抽象水晶盒 / 现代大厅 / 浮空岛）
> + 对其「AI 写程序盖」过程的实地抓取 + 本插件自己踩过的坑。
>
> **这份文档刻意不谈风格。** 风格决定"长什么样"，下面这些决定"能不能立住"。
> 换任何风格都必须满足。

---

## P1 体量先行：先定档位，再定细节

**唯一口径（硬规则，不由作者自选）**

| 档位 | 方块数 |
|---|---|
| **小建筑** | < 10,000 |
| **中型建筑** | 10,000 ~ 80,000 |
| **大型建筑** | ≥ 100,000 |
| 过渡带 | 80,000 ~ 100,000（口径未定义，必须明确归到中型或大型） |

**默认生成 = 中型建筑，方块数落在 20,000 ~ 50,000 左右。**

判定是**可执行的**：构建时 CLI 会打印
`SCALE 中型建筑 30,648 方块（目标区间 20k~50k ✓）`；
若判为中型却不在 20k~50k，会额外报 `[体量] 中型但不在默认区间`。

**结论**：不指定档位时，按中型 20k~50k 设计；用户要"更大"就明确升到大型（≥100k），
要把尺寸写进设计书的「体量」一节并在交付时自报档位。

**反例（我）**：为过 `PROPORTION_FLAT`（宽:高 >2.2 判死）把画布压到 52×28×52、6.5k 方块，
按这套口径**只算小建筑**，却当成"八色大厅"交付。

## P2 竖向必须有锚，而且不止一根

**规律**：不论东方塔、西式城堡还是抽象结构，画面里都有**多根**高出主体的竖线
（8 座塔 + 8 道光柱 / 多层飞檐 / 尖顶群）。竖向锚点决定了天际线。

**反例（我）**：第一版只有 1 根中央塔，其余全是平地，剪影是一块圆盘。

**做法**：≥3 段高度变化；竖向元素的数量与主体数量挂钩（多塔则多锚），不要只放一根"地标"。

---

## P3 形体用参数生成，不逐格手摆

剖面表 `[[层, 半径, 材质], ...]` 旋转成形，可表达：
- 中式飞檐（凹曲收分）、哥特尖顶（凸曲收分）、现代曲面（直锥）、倒锥悬空岛

**风格只改剖面曲线与材质词，不改生成方式。**

**反例（我）**：圆顶逐层写死半径，收分差值大于壳厚 → 相邻环径向不相交 → 55 块脱节。

**做法**：任何旋转对称体都写剖面表；生成前先算"相邻层半径差 ≤ 壳厚"。

---

## P4 颜色按「角色」分档，不按「色相」分色

**规律**：每个色系给 5 个角色，而不是 1 个颜色。

| 角色 | 用途 |
|---|---|
| wall | 主墙 |
| deep | 暗部 / 凹进 / 门套 |
| roof | 屋顶 / 檐口 |
| glass | 开窗 / 发光面 |
| tone | 浅调铺地 / 过渡 |

**这条与风格完全无关**：东方仙宫要朱红+金，西式城堡要石灰+深石，现代要白+黑，
但**都需要"同一色系内的明暗层次"**，否则大面积同色必然廉价。

**反例（我）**：每队只给 1 种 wool，8 色上完像色卡。

---

## P5 接缝靠绘制顺序解决，不靠事后修补

**规律**：明确"后画覆盖先画"，并给被覆盖件算停止边界。
（例：先桥后塔 → 塔平台自然覆盖桥端；栏杆/桥底停在塔平台外沿）

**风格无关**：任何多体量拼接（城+墙、殿+廊、塔+桥）都靠这个消接缝。

**反例（我）**：桥与塔各自画，接缝处既有多余栏杆又有穿插，只能靠悬空闸门事后发现。

---

## P6 入口是「可通行空间」，不是「一扇门」

**规律**：判定标准是**人能不能走过去**——
- 门/门洞净空 ≥2 格（实际常用 4~6 格）
- 门槛相对室外地面高差 ≤1 格，超了必须补台阶
- 门内侧不得被地板/家具堵住
- 入口前后贯通，不是死胡同

**风格无关**：谷仓用空门洞、神庙用拱门、现代用玻璃门厅，判据都一样。
**且不要为了"有门"硬装门板**——棚屋/废墟/工地本来就没有门。

---

## P7 装饰必须有承托，且要单独报

**规律**：灯笼 / 旗 / 藤 / 锁链 / 栏杆 / 火把 这类附着件，必须能指出"它靠什么立住"，
并在自检里**逐项报数量**（它报"24 items 没支撑 → 游戏里会掉"）。

**反例（我）**：装饰完全不检查；本轮新写的 `supportReport` 一上线就抓出自己旧建筑 3 处悬空。

---

## P8 配色有上限，颜色靠「分区 + 材质」承载

**规律**：主体配色分组 ≤3~4；要表达 8 种标识色时，用**不计入主体统计的材质**
（wool / 染色玻璃 / 未映射的混凝土），把彩色混凝土留给 2~3 色的场合。

**这不是钻检测器的空子**：把多色压在少数几组里，本来就是"8 色同时出现也不脏"的办法。

---

## P9 先算后写：设计期把几何算完

**规律**：写代码之前先做数值推演——
- 该点半径是否越出墙带（`r=√(8.6²+3.4²)=9.25 > 8.8 → 跑到墙外了`）
- 相邻层是否径向重叠
- 净空是否够站人
- 宽高比是否合理
- 部件停止边界在哪

**反例（我）**：靠生成后的闸门发现错误，同一次建筑返工 6~8 轮；而真正的结构错
（桥接不到塔、塔变孤立体）闸门给的数字是"12,214 悬空"，很难一眼看出根因。

**做法**：设计书写进文件（本插件 `output/design/*.md`），每项带算式。

---

## P10 会砍：每个元素先估代价

**规律**：加元素前先问"它要不要额外连通 / 支撑 / 几何验证"；代价大于收益就换简化版。
（它的原文：悬空花园小岛要再连桥、代码 +40%、会遮挡剪影 → 改成广场花坛）

**风格无关**：这是**范围控制**，不是设计品味。

---

## P11 输出分段 + 完整性守卫

**规律**：长程序分段落盘，每段立刻语法检查 + 导出结构检查。
（它的死法：想了 735 秒、5.9k 字程序在第 134 行被截断 → 0 方块）

**做法**：`node --check` + `checkComplete(mod)`；程序超过 ~200 行就拆分。

---

## P12 机器分 ≠ 好看，必须能看清细节

**规律**：检测只能证明"没有硬伤"。验收要有能看清门窗/檐口/室内的手段
（剖面 / 重播 / 多视角 / 游戏内截图），否则等于闭眼打分。

**反例（我）**：用简渲等距图自评，门窗檐口完全看不出，却据此判"通过"。

---

## P13 版本化迭代

**规律**：作品库每件都带版本数（1~4 版），可回滚对比。改动一律存新版，不覆盖。

**做法**：修订号 + 历史快照；不要在原文件上连续改写。

---

## 一页速查（写 builder 前过一遍）

```
□ 规模：跨度≥50？方块≥20k？（P1）
□ 竖向：≥3 段高差？竖向锚≥2 根？（P2）
□ 形体：旋转体用剖面表？相邻层重叠？（P3）
□ 配色：每色 5 档角色？主体分组≤4？（P4/P8）
□ 顺序：写了绘制顺序表？被覆盖件有停止边界？（P5）
□ 入口：≥2 格净空、高差≤1、内侧不堵？（P6）
□ 装饰：每件能说出承托？（P7）
□ 预检：半径/净空/宽高比/层重叠都算过？（P9）
□ 范围：砍掉的高代价元素？（P10）
□ 程序：分段 + 语法/完整性检查？（P11）
□ 验收：有能看清细节的观察手段？（P12）
□ 版本：改动存新版？（P13）
```
