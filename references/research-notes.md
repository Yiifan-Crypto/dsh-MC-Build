## 一、它的流水线（实测）

```
用户提示词
  ↓
[可选] AI 规划构建：AI 先问风格/材质/景观 → 用户点选确认
  ↓
① 写造房程序     ← 长时间思考（735 秒 / 84k 字）→ 输出一段 JS 程序（5.9k 字）
  ↓

  ↓
③ 交付           ← 剖面 / 重播 / 框选 / 敲方块 / 创世神 继续编辑
```

关键指标（本次）：思考 735s、84k 字、程序 5.9k 字、**执行 0 秒 0 次调用 → 失败**。

## 二、它的程序骨架（最有价值的部分）

### 2.1 颜色不是单色，是「每队 5 档色阶」

```js
const COL = [
  { n:"黄", wall:"#e3bf3a", deep:"#a98a1c", roof:"#caa42a", glass:"#ffe066", tone:"#f6e7a6" },
  { n:"绿", wall:"#58a554", deep:"#3b7a3e", roof:"#46873f", glass:"#7ed47a", tone:"#bde3b4" },
  { n:"白", wall:"#efece1", deep:"#cfc9b8", roof:"#e0dccf", glass:"#ffffff", tone:"#ffffff" },
  { n:"蓝", wall:"#4a7fd6", deep:"#2f5aa6", roof:"#3c6cc0", glass:"#79b3ff", tone:"#b9d6f7" },
  { n:"紫", wall:"#9257cf", deep:"#6a3a9e", roof:"#7f47bd", glass:"#c493f5", tone:"#ddc4f4" },
  { n:"粉", wall:"#ef8ec6", deep:"#c8619f", roof:"#e277b4", glass:"#ffb3dd", tone:"#ffd4ea" },
  { n:"棕", wall:"#8d5a35", deep:"#633d22", roof:"#7a4a2a", glass:"#c08a5a", tone:"#dcb794" },
  { n:"红", wall:"#cf4b41", deep:"#992f28", roof:"#bb3b32", glass:"#ff7a6a", tone:"#ffb7ae" },
];
```

五个角色：**wall 墙色 / deep 暗部 / roof 屋顶 / glass 玻璃 / tone 浅调**。
→ 同一个队伍色有明暗层次，所以 8 色同时出现也不脏。
→ 对比我这边：每个队只有 1 种 wool，必然平淡、且被配色闸门逼成"点缀"。

### 2.2 写的是「颜色 + 材质词」，不是方块 ID

```js
block(x, y, z, "#9a948c 石");
cylinder(cx, y, cz, r, 1, "#d8d2c4 抹灰");
```

材质词表：`石 土 木 原木 冰 抹灰 金属 灯 布 玻璃 砖 宝石`
→ 平台负责把「色值 + 材质」解析成实际方块。这是它能做同色系降级、适配不同材质包的原因。

### 2.3 形体用「剖面表 + 旋转」（lathe）

```js
// 浮空岩岛：逐层给半径
const prof = [
  [F,    17.75, "#9a948c 石"],
  [F-1,  17.75, "#8a847c 石"],
  [F-2,  17.1,  "#7d7770 石"],
  [F-5,  13.4,  "#5f5a54 土"],
  [F-8,   5.8,  "#4a4540 石"],
];
for (const [y, r, m] of prof) cylinder(0, y, 0, r, 1, m);
```

→ 倒锥、穹顶、圆台、塔座，全部是「每层半径」一条数据。
→ 塔座同理：`[[F,9.9],[F-1,9.4],[F-2,8.5],[F-3,7.2],[F-4,5.6],[F-5,4.0],[F-6,2.4]]`。

### 2.4 放射布局用「局部坐标系 + 扇区函数」

```js
const t = i*45*D2R, ux = Math.cos(t), uz = Math.sin(t);   // 径向单位向量
const px = -Math.sin(t), pz = Math.cos(t);                 // 切向单位向量
const fx = -ux, fz = -uz;                                  // 朝向中心
const at = (a, b) => [cx + fx*a + px*b, cz + fz*a + pz*b]; // 局部 (a,b) → 世界

function angOf(x,z){ return (Math.atan2(z,x)/D2R+360)%360; }
function angDist(a,b){ let d=Math.abs(a-b)%360; return d>180?360-d:d; }
function nearSector(t){ return ((Math.round(t/45)%8)+8)%8; }
function faceDir(dx,dz){ return Math.abs(dx)>Math.abs(dz) ? (dx>0?"east":"west") : (dz>0?"south":"north"); }
```

→ 8 个区、8 座塔、8 条桥，全部由同一个函数绕 45° 生成，**天然对称、天然不重叠**。
→ `(a,b,r)` 局部坐标让"门开在朝着中心的那一面"变成 `a > 5.2 && |b| <= 2.3`。

### 2.5 施工顺序 + 覆盖(z-order)纪律（原文）

```
Final structure:
  1 island + rim lights
  2 plaza medallion
  3 railing + colonnade ring + columns + lanterns
  4 bridges ×8
  5 towers ×8
  6 center altar + hologram
  7 planters + pots + misc
  8 print
```

它明确靠**后画覆盖先画**来消除接缝：

> "the tower platform draws over the bridge ends (draw towers after bridges)"
> "the railing at a=24.5 would be overwritten by the platform... let me limit the bridge railing to a=17..22.5"
> "the bridge underside ... stop before the tower so it doesn't float through the tower's rock. Use a<=22.5"

→ 这是我没有的：我一直用 `put` 硬写，然后靠 `FLOATING` 闸门事后补救。

### 2.6 入口的做法（比我讲究）

```js
// 门洞：a 朝中心，h = 6（中间）/ 5（两侧）
if (a > 5.2 && Math.abs(b) <= 2.3) {
  const h = Math.abs(b) <= 1.2 ? 6 : 5;
  if (y <= F+h) continue;                  // 挖空
  if (y === F+h+1) m = "#5f5a54 抹灰";     // 过梁
}
// 门框：a > 4.6 && |b| <= 3.3 && y <= F+7 → c.deep  ← 加宽门套
// 门楣石：a≈8.3, b=0, y=F+7 → #c9a227 金属     ← 金色拱心石
// 门口地面：a>4.5 && |b|<=2.2 → c.wall+" 布"   ← 入口地毯
// 门口灯：平台两侧 y=F+1 直接放 lantern（有支撑）
```

→ 门 = **挖洞 + 门套 + 拱心石 + 地毯 + 门口灯**，5 件一起做，且高度 5~6 格（远超我 2 格的底线）。

## 三、它的思考方式（原文摘录）

### 3.1 写码前先算几何，算错当场推翻

> "the point (a=-8.6, b=3.4) has r ≈ sqrt(8.6²+3.4²)=9.25 > 8.8 → **outside the wall**! ...
> So the portal frame at |b|=2: r=sqrt(73.96+4)=8.83 → edge of the wall band ✓"

> "F-9 = -3 ✓, F-10 = -4 ✗. So the deepest is y=-3 → 应停在 F-9"

→ 它在纸面上做我这边 `FLOATING` 闸门的工作。

### 3.2 主动否决不可实施方案

> "wall_torch[facing=east] — direction depends on the wall's orientation,
> **complicated for diagonal towers**. Use hanging lanterns from chain instead."

> "Material 布 → wool block, **no stairs variant**. Better use 木 for benches.
> Slab of wool doesn't exist either."

→ 它按"方块有没有这个形态"来选方案，而不是硬塞。

### 3.3 会为了少写代码而砍需求（重要的克制）

> "a small floating garden island ... **They'd clutter the silhouette.**
> They should be walkable to make sense; connect with a bridge? **That's more code.**
> **Decision: keep it simpler — add 8 planter beds on the plaza itself.**"

→ 它明确权衡"效果/工作量"，主动砍掉。我这边常常越改越多。

### 3.4 收尾就把代码一次性写完

> "Alright. Also the bridge underside ... Now, the towers' rock supports ...
> **Let me now write the actual code.**"
> "Now write everything." / "Write the code."

## 四、它这次为什么失败（同样重要）

```
[提示] AI 的造房程序有一段没写完，先按写好的部分来
[提示] 程序跑完了（0 秒，调用造房函数 0 次），中途出错：
      SyntaxError: Unexpected end of input（第 134 行）
[提示] 程序没传完，请 AI 重新交一份完整的
```

**思考 735 秒 + 84k 字，产出的 5.9k 字程序在第 134 行被截断 → 0 方块。**

可学的两点：
1. **一次性输出长程序非常脆弱**。程序越长越容易断在半截。
2. **平台有"完整性守卫"**：它检测到语法不完整，明确告诉 AI "重新交一份完整的"，并且提示"先按写好的部分来"（降级可跑）。

→ 反过来说，我这边"分段 builder + 每段跑闸门"的路线在**抗截断**上更稳。

## 七、本插件已落地的实现

文件：`build-litematic/scripts/build_kit.cjs`

| API | 作用 | 实测 |
|---|---|---|
| `mat('#cf4b41','混凝土')` | 颜色+材质 → 方块，族内取最近色 | 可用 |
| `teamPalette('#cf4b41')` | 由 1 个主色派生 5 档（wall/deep/roof/glass/tone） | 可用 |
| `revolve(a,{cx,cz,profile:[[y,r,方块],...]})` | 剖面表旋转体（倒锥/穹顶/圆台） | 可用 |
| `ring(a,{cx,cy,cz,r,hole,name})` | 圆环壳 | 可用 |
| `frame(i,{count,cx,cz,radius})` | 放射分区局部坐标系，`at(a,b)` 取世界坐标 | 可用 |
| `angOf/angDist/nearSector` | 扇区角度工具（与 mcarch 同口径） | 可用 |
| `checkComplete(mod)` | 输出完整性守卫（对抗"程序被截断"） | 可用 |

### 已知限制（如实记录）

1. **颜色解析只能取"材质族内最近的方块"**。MC 在 `混凝土` 族里没有亮红色块，所以
   `#cf4b41` 会落到 `orange_concrete`（偏橙）。要精确控制颜色，用 `allow` 参数限定候选，
   或换材质词（如 `布`/`砖`）。
2. `抹灰` 族只放中性浅色块；**彩色墙体不要用 `抹灰`**，否则会被压到白色系。
3. 旋转体是实心填充（`hollow:true` 只留壳），不做内部分层，层数多时方块量增长快。

# MC 建筑学习总结

> 来源：① 对 mcarch.cn「AI 写程序盖」的实地观察（1 件完整作品 + 11 件作品库元数据）
> ② 本插件自己两轮建造踩出的 17 个真坑

## 一、最根本的一条分界

**机器能判的：结构是否正确。机器判不了的：好不好看。**

| 机器能判（已做成闸门） | 只能靠人/靠算 |
|---|---|
| 方块是否悬空、是否连通 | 剪影好不好看 |
| 门能不能走过去（1×2 碰撞箱） | 比例是否顺眼（数值只能筛掉极端） |
| 装饰有没有承托 | 配色是否高级 |
| 主体宽高比是否离谱 | 叙事、氛围、地标感 |
| 配色分组是否超载 | 细节密度是否恰到好处 |
| 输出是否被截断 | 风格是否统一（规则能查、观感要人） |

**教训**：用低清预览图自评，等于闭眼打分。我这次用简化等距图出手，门窗檐口完全看不出。

## 二、体量分档（唯一口径）

| 档位 | 方块数 |
|---|---|
| **小建筑** | < 10,000 |
| **中型建筑** | 10,000 ~ 80,000 |
| **大型建筑** | ≥ 100,000 |
| 过渡带 | 80,000 ~ 100,000（口径未定义，须明确归到中型或大型） |

**默认生成 = 中型建筑，20,000 ~ 50,000 方块。**

判定是可执行的：构建时 CLI 打印 `SCALE 中型建筑 30,648 方块（目标区间 20k~50k ✓）`；
判为中型却不在 20k~50k 会额外报 `[体量] 中型但不在默认区间`。

参考实例（作品库观察，仅供参考，不作为档位定义）：

| 作品 | 跨度 | 方块 | 按本口径 |
|---|---|---|---|
| 悬空玻璃水晶盒 | 9 | 386 | 小建筑 |
| 八色候场厅 | 41 | 10,292 | 中型（偏小） |
| 中天圣境·浮岛仙宫 | 64 | 23,592 | 中型 |
| 虚空学院 | 93 | 28,513 | 中型 |
| 八色传送门大厅 | 87 | 37,742 | 中型 |

## 三、可执行的方法（原语级）

### 1. 剖面表旋转（lathe）
```
profile = [[层y, 半径, 材质], ...]  →  rotate → 形体
```
同一套代码可表达：中式飞檐（凹曲收分）、哥特尖顶（凸曲）、现代直锥、倒锥悬空岛。
**风格只改剖面曲线与材质，不改生成方式。**

**坑 E-014**：空心壳厚度必须 ≥ 相邻层半径差，否则相邻环径向错开 → 脱节悬空；半径小于壳厚时改实心。

### 2. 局部坐标系 + 扇区函数（放射布局）
```js
frame(i, {count, cx, cz, radius}) → { ux,uz, px,pz, fx,fz, at(a,b) }
angOf(x,z) / angDist(a,b) / nearSector(t)
```
`a` 朝中心、`b` 切向。8 塔/8 桥/8 区由同一函数绕 45° 生成，天然对称不重叠。

**坑 E-013**：半径原点必须声明。「从塔心朝中心量 16.3」和「全局半径 16.3」数值相同、语义完全不同——混用会把桥画到广场上、塔变孤立体（实测报 12,214 悬空）。

### 3. 颜色按角色分 5 档
```
wall 主墙 / deep 暗部 / roof 屋顶 / glass 开窗 / tone 浅调
```
每个队伍色由 1 个主色派生 5 档。**这是"8 色同时出现也不脏"的真正原因。**

**坑 E-009**：每色只给 1 种方块 → 必然平淡像色卡。

### 4. 颜色+材质语义，不写方块 ID
```js
block(x, y, z, "#9a948c 石");   // 色值 + 材质词
```
材质词：石 / 抹灰 / 木 / 原木 / 土 / 冰 / 金属 / 灯 / 布 / 混凝土 / 玻璃 / 砖 / 宝石
由解析层映射到真实方块，**能报色差、能同族降级、换版本不崩**。

**坑**：不同材质族的可用方块差别很大（`抹灰` 全是中性浅色，拿它配饱和红会得到白色）；多色标识要选**不计入配色统计**的材质（wool / 染色玻璃 / 未分组混凝土），否则撞 `TOO_MANY_GROUPS`（坑 E-016）。

### 5. 绘制顺序 = 接缝处理手段
```
地面 → 走道 → 桥 → 主体 → 塔/楼 → 装饰
```
后画覆盖先画。**每个被覆盖件都要算"画到哪为止"**，例如栏杆/桥底停在塔平台外沿，否则出现断头栏杆、桥底穿塔。

**坑 E-011**：桥和塔各画各的，接缝靠事后闸门发现，代价大。

### 6. 入口是「空间」，不是「门」
- 门洞净空 ≥2 格（实际常用 4~6 格）
- 门槛相对室外地面高差 ≤1，超了必须补台阶
- 门内侧不得被地板/家具堵住
- 入口前后贯通
- **不必硬装门板**：棚屋/谷仓/废墟/工地本来就没有门，用 2 格高开放门洞

**坑 E-001**：门状态齐全 ≠ 能通过。地板铺在门洞里、门槛高 2 格、门后放箱子，都能让人进不去。必须显式声明 `entries` 并跑洪泛。

## 四、设计判断（机器判不了，要靠算和砍）

### 1. 先算后写
写代码前在纸面上算：该点半径是否越出墙带（`√(8.6²+3.4²)=9.25 > 8.8 → 墙外`）、相邻层是否重叠、净空够不够站人、部件停止边界。

**坑 E-009/P9**：靠事后闸门，同一次建筑返工 6~8 轮；而结构级的错（桥接不上塔）闸门只给"12,214 悬空"，看不出根因。

### 2. 竖向锚 ≥2 根
剪影 ≥3 段高差；竖向元素数量与主体挂钩（多塔则多锚）。只放一根"地标"= 圆盘带根针。

### 3. 会砍
加元素前先估它带来的**连通/支撑/几何验证成本**；代价大于观感收益就换简化版。
（观察到的实例：悬空花园小岛要再连桥、遮挡剪影、代码 +40% → 改成广场花坛）

### 4. 每栋建筑要有自己的风格
禁止翻旧 builder 抄尺寸/配色/布局。先定「地域 + 年代 + 用途 + 使用者」，再推导材质与形态；风格一旦定，全建筑统一（混搭是零容忍项）。

### 5. 版本化
改动存新版可回滚；观察到的作品每件 1~4 个版本。

| # | 坑 | 一句话教训 |

| E-001 | 门装上了人进不去 | 门状态齐全 ≠ 可通行，要验净空/门槛/内侧 |
| E-002 | 以为必须有门板 | 入口是空间，棚屋废墟用开放门洞 |
| E-003 | 一上来套尺寸 | 尺寸从功能长出来，至少打破一个维度 |
| E-004 | 抄上一栋参数 | 旧 builder 只当反例，不当模板 |
| E-005 | 用低清预览自评 | 机器分只证明没硬伤 |
| E-006 | 三体块挤成一团 | 主次靠体量差 + 间距 |
| E-007 | 屋顶盖过内容 | 屋顶内半径 ≥ 内容外半径 |
| E-008 | 角度扇区当平分 | 角度等分 ≠ 格子等分（实测偏差 8%） |
| E-009 | 每色只给一种颜色 | 一个色系 5 档角色 |
| E-010 | 曲面逐格摆 | 用剖面表旋转 |
| E-011 | 接缝靠事后补 | 画序 + 停止边界 |
| E-012 | 不停加细节 | 先估代价，砍掉高成本元素 |
| E-013 | 半径原点混用 | 桥画到广场上、塔成孤立体 |
| E-014 | 空心壳收分过快 | 壳厚 ≥ 相邻半径差 |
| E-015 | 悬空岛用接地判定 | 假悬空 18,825；要分接地模式/虚空模式 |
| E-016 | 多色用彩色混凝土 | 撞配色闸门，改用不计入统计的材质 |
| E-017 | 长程序一次输出 | 分段写 + 语法/完整性守卫（对方就死在这） |

## 六、闸门清单（当前插件已具备）

| 闸门 | 判什么 | 不过会怎样 |
|---|---|---|
| `aesthetic` grade | 配色分组/悬空/比例/剪影/细节密度 | `aesthetic=BLOCK` 阻断 |
| `walkable` | 门洞净空、门内侧、门槛高差、入口接近 | `walkable=BLOCK` 阻断 |
| `verify_reachable` | 从门外 BFS 能不能走到室内目标点 | 退出码 1 |
| `supportReport` | 灯笼/旗/藤/链/栏杆有没有承托 | 报数量与坐标 |
| `headroomReport` | 室内净空分布（≤2 / 3~5 / 6+ 格） | 分布数据 |
| `checkComplete` | 导出结构是否完整（防截断） | 报缺失项 |

## 七、仍然没解决的

1. **没有能看清细节的验收手段**。等距简渲只能看色块，门窗/檐口/室内/纹理都看不到。这是目前最大的盲区。
2. **比例闸门只能筛极端**。数值通过 ≠ 好看；多体量构图尤其需要人眼。
3. **配色"高级感"不可判**。5 档色阶是结构化的下限保证，不是上限。
4. **跨风格验证不足**。13 条原则里 P4/P5/P9 来自单件实现 + 本插件复现；P1/P7 有元数据支撑；其余未做跨风格抽样。
